\begin{abstract}
O SpinParty é uma aplicação Android, desenvolvida em Java, que escolhe
mini-jogos para grupos de amigos. O jogador faz girar o telemóvel; enquanto
roda, o ecrã mostra números e, quando a rotação pára, a aplicação sorteia um
mini-jogo e vibra para avisar o grupo. A aplicação usa o giroscópio, o
acelerómetro e a vibração do dispositivo e comunica com um serviço REST
(restdb.io) para obter os mini-jogos e os respetivos desafios e para guardar
jogadores e pontuações. Este relatório descreve o contexto, a análise, o
design, a implementação e os testes da aplicação.
\keywords{Android \and Jogos móveis \and Jogos de grupo \and Sensores \and API REST}
\end{abstract}


\section{Contexto}
\label{sec:context}
O SpinParty é um jogo de grupo para Android. O jogador coloca o telemóvel a
girar; enquanto roda, passam números no ecrã e, quando o telemóvel pára, é
sorteado um mini-jogo. Os jogadores acumulam pontos ao longo das rondas.

Os mini-jogos previstos são: \emph{Reflexos} (ganha quem pegar primeiro no
telemóvel quando o ecrã fica verde), \emph{Batata quente} (o telemóvel passa
entre jogadores até ``explodir'') e \emph{Contar vibrações} (adivinhar o
número de vibrações).

A aplicação explora três funcionalidades do dispositivo: o giroscópio, para
detetar a rotação; o acelerómetro, para detetar movimento nos mini-jogos; e a
vibração, como \emph{feedback} e mecânica de jogo. Comunica com o serviço REST
restdb.io, de onde obtém os mini-jogos e os desafios.

Aplicações semelhantes:
Existem aplicações semelhantes que usam o telemóvel como "roleta" para jogos
de grupo, como a \emph{Heads Up!} e a \emph{Jackbox Party Pack}, que também
escolhem desafios aleatórios para jogar em grupo. O SpinParty distingue-se
por usar diretamente os sensores de movimento do telemóvel (giroscópio e
acelerómetro) como forma de interação, em vez de apenas toques no ecrã, e por
guardar os mini-jogos e os jogadores num serviço REST externo (restdb.io), o
que permite atualizar o catálogo de mini-jogos e desafios sem alterar a
aplicação.


\section{Análise}
\subsection{Requisitos funcionais}
\begin{itemize}
\item RF1: detetar a rotação do telemóvel e sortear um mini-jogo quando pára.
\item RF2: obter os mini-jogos e os desafios do serviço REST (GET).
\item RF3: criar jogadores (POST).
\item RF4: atualizar a pontuação dos jogadores no fim de cada ronda (PUT).
\item RF5: mostrar as pontuações no fim do jogo.
\end{itemize}

\subsection{Requisitos não funcionais}
Seguindo a classificação FURPS+, os requisitos não funcionais são os seguintes.
\begin{itemize}
\item \textbf{Usabilidade:} a aplicação tem uma interface gráfica tátil.
\item \textbf{Fiabilidade e desempenho:} não foram identificados requisitos
específicos.
\item \textbf{Suportabilidade:} a aplicação destina-se à plataforma Android,
com API mínima 29, e deve ter testes automáticos.
\item \textbf{Restrições de implementação:} a aplicação é desenvolvida em Java,
no Android Studio, e a demonstração tem de ser feita num dispositivo real.
\item \textbf{Restrições de interface:} a comunicação com o serviço remoto é
feita por REST, com dados em JSON.
\end{itemize}

ter vários Desafios associados.

\section{Implementação}
\subsection{Deteção da rotação com o giroscópio}
A classe \texttt{SpinActivity} regista-se como \texttt{SensorEventListener}
do giroscópio em \texttt{onResume} e anula o registo em \texttt{onPause}.
Em \texttt{onSensorChanged} é lido o valor absoluto da velocidade de rotação
no eixo $z$. Se for superior a 2, considera-se que o telemóvel está a girar e
mostra-se um número aleatório; quando passam mais de 500 ms sem rotação, o
jogo sorteado é mostrado e o telemóvel vibra durante 400 ms.


\begin{lstlisting}[numbers=left, basicstyle=\small\ttfamily]
public void onSensorChanged(SensorEvent event) {
  float z = Math.abs(event.values[2]);
  long now = System.currentTimeMillis();
  if (!hasResult && z > 2) {
    isSpinning = true;
    lastSpinTime = now;
    currentNumber = random.nextInt(jogos.size()) + 1;
    tvNumber.setText(String.valueOf(currentNumber));
  } else if (isSpinning && now - lastSpinTime > 500) {
    isSpinning = false;
    tvResult.setText(jogos.get(currentNumber - 1).getNome());
    vibrate();
    hasResult = true;
  }
}
\end{lstlisting}

\subsection{Comunicação com o restdb.io}
A classe \texttt{RestDbClient} faz os pedidos HTTP com \texttt{HttpURLConnection}
(sem bibliotecas externas), numa \emph{thread} à parte, nunca na principal.
Cada pedido leva o cabeçalho \texttt{x-apikey} com a chave da API, lida de
\texttt{local.properties} e exposta à aplicação através do \texttt{BuildConfig},
para a chave nunca ficar no código nem no repositório Git.

\begin{lstlisting}[numbers=left, basicstyle=\small\ttfamily]
public String get(String path) throws IOException {
    URL url = new URL(baseUrl + path);
    HttpURLConnection connection = (HttpURLConnection) url.openConnection();
    connection.setRequestMethod("GET");
    connection.setRequestProperty("x-apikey", apiKey);
    int code = connection.getResponseCode();
    if (code != HttpURLConnection.HTTP_OK) {
        throw new IOException("Resposta HTTP " + code);
    }
    return readAll(connection.getInputStream());
}
\end{lstlisting}

O \texttt{MiniJogoRepository} usa este cliente para obter os mini-jogos
(\texttt{GET /minijogos}) e o \texttt{MiniJogoJsonParser} converte a resposta
JSON em objetos \texttt{MiniJogo}. Se o pedido falhar (sem rede, chave errada,
etc.), o repositório usa uma lista local como alternativa, para a aplicação
continuar a funcionar sem ligação:

\begin{lstlisting}[numbers=left, basicstyle=\small\ttfamily]
public void carregarMiniJogos(Callback callback) {
    if (!client.isConfigured()) {
        callback.onErro("Falta configurar RESTDB_BASE_URL e RESTDB_API_KEY");
        return;
    }
    executor.execute(() -> {
        try {
            String json = client.get("/minijogos");
            List<MiniJogo> lista = MiniJogoJsonParser.parse(json);
            mainHandler.post(() -> callback.onSucesso(lista));
        } catch (IOException | JSONException e) {
            mainHandler.post(() -> callback.onErro(e.getMessage()));
        }
    });
}
\end{lstlisting}

\subsection{Criação de jogadores}
Quando um jogador é adicionado, o \texttt{JogadorRepository} cria um registo
na coleção \texttt{jogadores} do restdb.io, por \texttt{POST}, com o nome e a
pontuação inicial a 0. Se este pedido falhar, o jogo continua na mesma,
apenas com o jogador guardado localmente, porque a gravação remota não é
essencial para jogar:

\begin{lstlisting}[numbers=left, basicstyle=\small\ttfamily]
JSONObject corpo = new JSONObject();
corpo.put("nome", nome);
corpo.put("pontuacao", 0);
String resposta = client.post("/jogadores", corpo.toString());
JSONObject obj = new JSONObject(resposta);
Jogador jogador = new Jogador(obj.getString("_id"), nome, 0);
\end{lstlisting}

\subsection{Reflexos: deteção de movimento com o acelerómetro}
No mini-jogo Reflexos, o telemóvel fica pousado na mesa e, ao fim de um
tempo aleatório (entre 2 e 5 segundos), o ecrã fica verde. O jogador que
pegar primeiro no telemóvel ganha. A deteção de que o telemóvel foi
levantado usa o acelerómetro: é calculada a força total nos três eixos e
comparada com a força da gravidade em repouso; uma diferença grande
significa que o telemóvel foi mexido.

\begin{lstlisting}[numbers=left, basicstyle=\small\ttfamily]
public void onSensorChanged(SensorEvent event) {
  float x = event.values[0];
  float y = event.values[1];
  float z = event.values[2];
  double forca = Math.sqrt(x * x + y * y + z * z);
  boolean mexeu = Math.abs(forca - SensorManager.GRAVITY_EARTH) > 3;
  if (!mexeu) return;
  // ... regista o tempo de reação ou a batota
}
\end{lstlisting}

Para evitar deteções falsas logo ao colocar o telemóvel na mesa, a aplicação
ignora os eventos do sensor durante os primeiros 1500 ms da ronda.

\subsection{Contar Vibrações e feedback por vibração}
A vibração é usada em dois papéis distintos: como \emph{feedback} (por
exemplo, quando o mini-jogo é sorteado ou quando o ecrã do Reflexos fica
verde) e como mecânica de jogo, no mini-jogo Contar Vibrações, onde o
telemóvel vibra um número aleatório de vezes (entre 3 e 8) e o jogador tem
de adivinhar quantas foram. Cada vibração é agendada com
\texttt{Handler.postDelayed}, com um intervalo aleatório entre elas, para
não ser possível contar pelo ritmo:

\begin{lstlisting}[numbers=left, basicstyle=\small\ttfamily]
long tempo = 1500;
for (int i = 0; i < numeroCerto; i++) {
    handler.postDelayed(this::vibrarUmaVez, tempo);
    tempo += 400 + random.nextInt(800);
}
handler.postDelayed(this::perguntar, tempo + 1000);
\end{lstlisting}

\subsection{Batata Quente e os desafios}
No Batata Quente, o telemóvel mostra perguntas enquanto passa de jogador em
jogador, e "explode" ao fim de um tempo aleatório (entre 15 e 30 segundos),
escondido dos jogadores. O \texttt{DesafioRepository} fornece as perguntas
associadas a este mini-jogo; cada vez que se carrega em "Passar", mostra-se
uma pergunta nova, escolhida ao acaso.

\subsection{Modelo da partida e pontuações}
A classe \texttt{Partida} centraliza o estado de uma partida em curso: os
jogadores (nomes, por ordem de entrada), a pontuação de cada um e os
mini-jogos já jogados nessa partida, para não se repetirem. Só existe uma
instância em cada momento (\texttt{Partida.getAtual()}), partilhada por
todos os ecrãs:

\begin{lstlisting}[numbers=left, basicstyle=\small\ttfamily]
public void marcarJogado(String tipo) {
    jogosJogados.add(tipo);
}

public boolean jaJogou(String tipo) {
    return jogosJogados.contains(tipo);
}
\end{lstlisting}

O \texttt{SpinActivity} usa estes dois métodos para só sortear mini-jogos
ainda não jogados; quando falta apenas um, a aplicação salta a rotação e
mostra-o diretamente, já que não há escolha a fazer.

A pontuação de cada jogador (\texttt{darPontos}) é guardada na
\texttt{Partida} e também atualizada no restdb.io por
\texttt{JogadorRepository.atualizarPontuacao} (\texttt{PUT /jogadores/\{id\}}),
para o ranking final poder ser consultado a partir do servidor.

\subsection{Modelo de classes}
A Figura~\ref{fig:classes} mostra as principais classes da aplicação,
organizadas em três pacotes: \texttt{model} (as entidades do domínio),
\texttt{data} (acesso aos dados, local e remoto) e as classes de ecrã
(\emph{Activities}).

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{figures/diagrama_classes.png}
    \caption{Diagrama de classes da aplicação SpinParty.}
    \label{fig:classes}
\end{figure}

\begin{itemize}
  \item \textbf{Pacote \texttt{model}:} \texttt{Partida}, \texttt{Jogador},
  \texttt{MiniJogo} e \texttt{Desafio}, as entidades descritas no modelo de
  domínio (Secção~\ref{sec:context}).
  \item \textbf{Pacote \texttt{data}:} \texttt{RestDbClient}, que faz os
  pedidos HTTP ao restdb.io; \texttt{MiniJogoRepository} e
  \texttt{JogadorRepository}, que escondem das \emph{Activities} se os dados
  vêm do serviço REST ou da lista local; \texttt{MiniJogoJsonParser}, que
  converte o JSON da resposta em objetos \texttt{MiniJogo}; e
  \texttt{DesafioRepository}, com os desafios do Batata Quente.
  \item \textbf{\emph{Activities}:} \texttt{MainActivity} (ecrã inicial, onde
  se adicionam os jogadores), \texttt{SpinActivity} (ecrã do giroscópio, onde
  se sorteia o mini-jogo), e um ecrã por mini-jogo:
  \texttt{ReflexosActivity}, \texttt{BatataQuenteActivity} e
  \texttt{ContarVibracoesActivity}.
\end{itemize}

Cada repositório de dados (\texttt{MiniJogoRepository},
\texttt{JogadorRepository}) usa internamente o \texttt{RestDbClient} para
comunicar com o restdb.io numa \emph{thread} à parte, e devolve o resultado
à \emph{Activity} através de uma interface \texttt{Callback}, para nunca
bloquear a interface gráfica à espera da rede.

\subsection{Organização do código}
O código está organizado em pacotes Java, dentro de
\texttt{com.example.spinparty}:
\begin{itemize}
  \item \texttt{model} — as entidades do domínio (Secção~\ref{sec:context}).
  \item \texttt{data} — acesso aos dados: o cliente REST, os repositórios e o
  \emph{parser} do JSON.
  \item o pacote raiz (\texttt{com.example.spinparty}) — as \emph{Activities},
  um ecrã por classe.
\end{itemize}
Esta separação permite que as \emph{Activities} não saibam se os dados vêm
do restdb.io ou da lista local: essa decisão fica só nos repositórios.

\subsection{Navegação entre ecrãs}
A navegação é feita com \emph{Intents} explícitos entre \emph{Activities}:
o \texttt{MainActivity} abre o \texttt{SpinActivity} depois de haver pelo
menos dois jogadores; o \texttt{SpinActivity} abre a \emph{Activity} do
mini-jogo sorteado (\texttt{ReflexosActivity},
\texttt{BatataQuenteActivity} ou \texttt{ContarVibracoesActivity}); e, no
fim de cada mini-jogo, volta-se ao \texttt{SpinActivity} para sortear o
seguinte, até todos os mini-jogos terem sido jogados nessa partida.

\section{Conclusão}
\label{sec:conclusao}
O SpinParty cumpre o essencial do que foi proposto: deteta a rotação do
telemóvel pelo giroscópio, sorteia mini-jogos sem repetição numa partida,
usa o acelerómetro e a vibração como mecânica dos mini-jogos Reflexos e
Contar Vibrações, e comunica com o restdb.io para obter os mini-jogos e os
desafios (GET), criar jogadores (POST) e atualizar as suas pontuações
(PUT), com uma lista local como alternativa caso a ligação falhe. No fim
de cada partida, a aplicação mostra a pontuação dos jogadores e um ranking
obtido do servidor.

A maior dificuldade foi coordenar o acesso à rede com o ciclo de vida das
\emph{Activities}: os pedidos ao restdb.io correm numa \emph{thread} à
parte e só podem alterar o ecrã depois de confirmar que a \emph{Activity}
ainda existe (\texttt{isFinishing()}/\texttt{isDestroyed()}), para evitar
exceções quando o utilizador sai do ecrã antes da resposta chegar. Também
foi preciso ajustar os limiares de deteção do acelerómetro no Reflexos, para
